Explain a query

Paste a query: an old report's, or one you wrote in SSMS. v_Where explains each view and column it uses, flags what could go wrong, and converts it between the plain version (for SSMS) and the SSRS version (fn_rbac_, so reports respect console permissions). It all happens in your browser; the query isn't sent anywhere or saved.

How v_Where works

ConfigMgr keeps what it knows about devices in hundreds of SQL views (read-only tables) with names that don't say what they hold. v_Where finds the right ones for you and builds the report, without anyone writing SQL.

  1. Search in plain words: ram, last boot, bitlocker. Results list the views that hold it, with the matching columns highlighted.
  2. Click + next to the columns you want, from as many views as you need. Each one goes into your Report draft.
  3. Open Report draft. v_Where lines the views up by device, explains each connection in plain English, and gives you the SQL or a ready-to-upload ConfigMgr report (.rdl). Add filters there, or with the funnel next to any column.

Why is there a "join" when I only clicked +?

Columns from different views live in different tables. To show them side by side, one row per device, the tables have to be matched up by each device's ID. In SQL that matching is called a join. Clicking + says "I want this column"; v_Where works out the joins for you, and the Report draft lists each one in plain English.

Words you'll see

ViewA read-only table ConfigMgr provides for reporting. Think of one sheet in a workbook.
ColumnOne piece of data in a view, like a column header on that sheet: LastBootUpTime0, Model0.
Device IDResourceID: the number ConfigMgr gives each device. It's in most views, and it's how views are lined up.
Connection (join)Putting columns from different views side by side by matching device IDs. v_Where writes these.
Link tableA view holding two kinds of ID (for example user and device), added when two views share no ID directly.
One row per deviceMost views have one row for each device. Some have several (one per disk, program or update); v_Where warns you.
v_R_, v_RA_Discovery: devices and users found in Active Directory and on the network.
v_GS_Hardware inventory: the latest snapshot each device reported.
v_HS_Inventory history: earlier values. Most reports want v_GS_ instead.
v_CH_Client health: whether the ConfigMgr client is working and checking in.
Trailing 0In Model0 or Name0 it's just ConfigMgr's naming habit for inventory columns. Ignore it.
Not collected by defaultThe view exists, but ConfigMgr doesn't gather that data until someone turns it on (Client Settings, Hardware Inventory, Set Classes).
fn_rbac_Permission-filtered versions of views. Built-in ConfigMgr reports use them so people only see the devices their console role allows.
CollectionA group of devices or users in ConfigMgr. Reports usually ask which one to run against.
Readable valuesRaw numbers and codes turned into words: memory in GB, 1/0 as Yes/No, status codes as names.
.rdlA report file for SQL Server Reporting Services, which the ConfigMgr console's Reporting node uses.

Is it safe to use?

v_Where never connects to a ConfigMgr database. It searches a file of view and column names, with no device or user data in it. The SQL and reports it writes only read data, and only when someone runs them.

Schema-only reference: view and column names and types. No ConfigMgr data.
